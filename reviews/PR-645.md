## What the PR does

Follow-up to PR 573 (the websocket frame reorder fix). While libunit waits
for SHM_ACK, `nxt_unit_wait_shm_ack()` reads on and puts every other
message into `pending_rbuf`. Before this PR, each waiting message kept a
whole read buffer of 16496 bytes. Now the call site uses
`nxt_unit_read_buf_shrink()`, the same helper the PR 573 gate already
uses. A 20-byte message now waits in about 76 bytes.

The PR also adds two test helpers under `#if (NXT_TESTS)`
(`nxt_unit_test_port_queue()`, `nxt_unit_test_wait_shm_ack()`) and one new
`nxt_unit_msg_test` case that queues 8 messages plus a SHM_ACK and checks
that the held bytes are far below `8 * 1024`.

CHANGES and `docs/changes.xml` now name Java among the applications that
get the PR 573 fix through libunit.

## Findings

- `src/nxt_unit.c:4451-4457`: nit: `nxt_unit_test_port_queue()` returns
  `void *`. The caller casts to `nxt_port_queue_t volatile *` by hand. A
  wrong cast compiles clean. The `void *` keeps `nxt_port_queue.h` out of
  the public `nxt_unit.h`, which is a fair trade for a test-only helper.
  Fix, if you want type safety: forward-declare the queue type in
  `nxt_unit.h` under the same `#if (NXT_TESTS)`.

## Checked, no finding

- `src/nxt_unit.c:4986`: the shrink happens with the context mutex
  unlocked. `nxt_unit_read_buf_shrink()` releases the old buffer through
  `nxt_unit_read_buf_release()`, which locks the mutex itself. No
  recursion, no deadlock. The same pattern as `nxt_unit_process_read_msg()`
  at `src/nxt_unit.c:1193`.
- After the shrink, `nxt_unit_is_quit()` at `src/nxt_unit.c:4994` reads the
  shrunk copy. The copy keeps `size` and the message bytes, so the check
  works on it.
- On an allocation failure `nxt_unit_read_buf_shrink()` returns the whole
  buffer, and that buffer waits. Same failure mode as the PR 573 gate. The
  comment at `src/nxt_unit.c:3440-3447` documents it.
- `oob` sits before `buf` in `nxt_unit_read_buf_t`, so a shrunk copy keeps
  the out-of-band data with any attached fds. The fds stay open until the
  message leaves `pending_rbuf`, as before.
- MMAP messages still bypass `pending_rbuf` inside the wait loop. That is
  the PR 573 design; this PR does not change it.
- The new helpers are inside the `#if (NXT_TESTS)` blocks in
  `src/nxt_unit.h:472-491` and `src/nxt_unit.c:4362-4540`. The
  `check-test-hooks` gate stays happy.
- CHANGES and `docs/changes.xml` carry the same new wording, and each file
  keeps its own spacing style. The entry lives in the open 1.37.1 block;
  no `1.37.1` tag exists yet, so the block is not a shipped record.
- The PR keeps no bound on `pending_rbuf`. The body explains why: the
  context cannot stop reading, because SHM_ACK and MMAP arrive on the same
  port behind the queued messages, and flow control belongs in the router.
  Sound reasoning.
